# 研究职责（Research mandates）迭代计划

提出于 2026-10-09。参照「目标 / KPI / 约束定义一名数字员工」的个人助理设计，把 Wisp 已有的定时任务、助理派活、IM 通道、每日回顾和记忆串成「一份长期职责」。

## 为什么是这六步

对照之后，Wisp 缺的不是执行环境，而是职责这一层：

| 需要 | Wisp 已有 | 缺口 |
| --- | --- | --- |
| Goal / KPI / Constraints | 定时任务只有提示词和频率 | 没有职责对象，约束不映射到审批 |
| 每轮结束安排下一轮 | 固定间隔的 `schedules`、`/timer` | 下次时间不由进展决定，回合之间没有结构化状态 |
| 主动找用户 | 助理审批转交到微信 | 只有「审批」，没有「等你补条件」 |
| 定期汇报 | 每日回顾按天归纳记录 | 不按职责算 KPI 差距 |
| 反馈进入后续工作 | 记忆提议、全局与项目记忆 | 反馈改不了职责；记忆只增不整理 |

不做：云电脑、云端记忆服务。科研数据和算力本来就在用户自己的机器与服务器上。

## 迭代

- [x] **1. 职责对象**：`mandates` 表、DTO、自动化页的职责卡片与表单、四个科研模板；每轮注入目标 / KPI / 约束；「先问我」并入审批下限。
- [x] **2. 回合账本与自排程**：`end_round` 工具、`mandate_rounds` 表；下一轮时间由 Agent 建议并夹在约束边界内；每天回合上限；简报带上最近几轮账本。
- [ ] **3. 需要你**：`request_assistance` 工具，职责转为等待并暂停排程；推送到助理对话与 IM；回复后立即继续。等待一个 Run 结束。
- [ ] **4. 职责汇报**：按汇报节奏生成带引用的汇报（已完成、KPI 差距、阻塞、下一步），推送并留档。
- [ ] **5. 反馈环与记忆整理**：长期要求经确认后写入职责；内置「记忆整理」提出合并与淘汰建议；职责结束。
- [ ] **6. 助理作为主管**：助理读取全部职责并代为回复；IM `/mandates`；研究日历显示汇报与阻塞。

每个迭代一个提交，各自带测试和文档。用户文档在 [docs/research-mandates.md](../../research-mandates.md)。

## 与最初设想的出入

- **职责不挂 `schedules` 行**。最初设想让职责指向一条定时任务，再让 `end_round` 改它的下次时间。实际职责自带 `next_run_at`：定时任务的时间是锚定在固定节拍上的，而职责每一轮自己决定下一轮；复用还会让职责出现在定时任务列表和原生客户端里，并被「删除对话时清空 `frame_id`」的逻辑牵连。到点扫描和原子认领与定时任务同构，由同一个调度轮询驱动。
- **回合绑定一条固定对话，而不是每次新建**。职责的连续性靠这条对话的历史加每轮现取的简报，旧历史交给现有的归档式压缩。
- **`end_round` 不强制、不终止回合**。最初设想回合「必须」用它收尾。实际没有调用时由 Wisp 代记一条账本，保证连续；调用后模型仍可写几行给研究者再结束。
- **职责规则放在 `wisp-app` 而不是 `src-tauri`**，这样无头 eval 能注册同一个 `end_round` 并对着真实账本跑。

## 边界

- 仅在 Wisp 运行时触发，沿用定时任务的既有限制；常驻后台进程不在本计划内。
- 职责是本机状态，不随项目导出、导入或同步。
- 原生 macOS / Windows 客户端不在本计划内。
