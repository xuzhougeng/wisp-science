# 项目数据库不可用时的安全排查

如果打开项目或会话时看到 `Project <id> database is unavailable: <path>`，Wisp 当前无法访问错误中所列路径的项目数据库。这个错误本身不能说明数据库一定损坏，也不能说明其他项目的会话数据已经丢失。可能原因包括工作区被移动或删除、磁盘或同步盘暂时不可用，以及权限或数据库文件异常；应先核对错误路径和完整错误信息。

## 先保护数据

1. 完全退出 Wisp，确认应用已关闭。
2. 将仍然存在的整个项目目录（至少包括 `.wisp`）复制到另一个位置。保留 `project.sqlite` 以及旁边可能存在的 `project.sqlite-wal`、`project.sqlite-shm` 或 journal 文件。如果使用集中存储，或错误影响其他项目，也应备份应用数据目录中的 `wisp.sqlite` 及其旁路文件；使用云盘文件夹快照时还需保留应用数据中的 `project-cache/`。不要只复制主数据库文件，也不要删除、重命名或覆盖这些文件来尝试“重建”数据库。
3. 如果项目位于外接盘、网络盘或同步目录，先确认该卷已挂载、同步已完成，并且当前用户对项目目录有读写权限。核对错误提示中的登记路径；若移动过工作区，优先恢复到原路径或重新连接设备，再启动 Wisp。不要在缺失路径创建空数据库来代替原数据。

## 缺失项目的登记与版本差异

[问题 #1422](https://github.com/xuzhougeng/wisp-science/issues/1422) 已确认：在 Wisp Science 1.16.0 中，一个已登记项目的数据库缺失可能阻断其他正常项目的会话加载和发送，且 **删除 → 仅从 Wisp 移除** 也可能返回同一错误。

运行时修复 [PR #1424](https://github.com/xuzhougeng/wisp-science/pull/1424) 已合并到 `main`。这不表示已安装的版本一定包含修复；应确认所用构建包含该变更。包含修复的构建会按已知项目或会话归属访问数据库，允许集中存储及其他可用项目的会话继续加载和保存。直接访问缺失项目仍会明确报错，不会创建空库，也不会回退到全局库中的过期记录。未限定项目的跨项目搜索或安全检查仍可能报告不可用的项目库。

如果工作区已删除且不需要恢复，或只想从列表移除不可用项目，在包含修复的构建中选择 **删除 → 仅从 Wisp 移除**。数据库确实缺失时，此操作可解除登记并保留仍存在的工作区文件；它不会恢复已删除的数据。**删除项目及本地数据** 会删除文件，不能用作故障恢复，而且仍需通过数据库相关的删除检查。数据库损坏、权限或身份不匹配等错误不会被当作“文件缺失”绕过检查。详见[项目同步说明](project-sync.md)。

如还需通过项目同步恢复，移除前先确认其他已授权设备或已有设备码可用于重新建立同步。解除登记也会清除本机保存的项目同步密钥及游标，但不会删除远端历史。

如果旧版本连“仅从 Wisp 移除”也失败，先保留备份并升级到包含修复的构建，或请维护者根据具体错误协助处理。不要清空全局数据库、批量删除项目登记或清理其他项目数据。

## 最后再尝试历史快照恢复

仅在原项目数据库、应用数据库、导出的项目包及同步版本均无法用于恢复时，才在备份完成后使用 **导入项目 → 从工作区恢复会话**，从原工作区 `.wisp/history` 中恢复可用的历史快照。此功能是尽力恢复：它只能导入确实保存在这些快照中的消息，不能替代完整项目数据库备份，也不一定包含普通对话或项目级记录。完整迁移应使用 Wisp 的项目目录或 ZIP 导出/导入。详见[项目迁移说明](project-transfer.md)。

历史快照恢复仅适用于未登记、且没有现有项目存储元数据的孤立文件夹。若文件夹已登记，或仍有 `.wisp/project.sqlite`、`.wisp/project.json`，恢复入口会拒绝处理；此时应保留原文件并请维护者协助，不要删除或重命名元数据来强行绕过检查。

若错误仍在，保留原始目录和备份，记录 Wisp 版本、操作系统版本、项目是否曾移动或同步、脱敏后的错误路径，以及 `.wisp` 中数据库和旁路文件的文件名与大小，并随 issue 提交。不要将数据库文件上传到公开 issue，因为其中可能包含私人会话内容。

如果其他项目也无法打开会话，请注明跨项目影响，并核对各项目报错是否指向同一个失效路径。单个项目数据库不可用不代表所有会话数据都已丢失，也不应直接对正常项目执行历史快照恢复。
